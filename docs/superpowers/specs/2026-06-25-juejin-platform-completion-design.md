# 掘金平台接入完善设计

## 目标

按照 MediaCrawler 现有平台结构完善掘金平台，使其成为 CLI、Web API 和 WebUI 中的一等平台，并确保搜索、指定文章、创作者三种抓取模式及数据落库能够可靠工作。

## 范围

本次工作包含：

- CLI 支持 `--platform juejin`，兼容现有搜索、详情、创作者、评论、子评论、数量限制、代理、断点续传和存储参数。
- Web API 的平台枚举、请求校验、命令构建和数据统计支持 `juejin`。
- WebUI 平台选择器支持掘金，并可正确向现有 API 提交掘金任务。
- 掘金文章、评论、子评论和创作者数据支持 CSV、JSON、JSONL、Excel、SQLite、MySQL、PostgreSQL 和 MongoDB 等现有存储方式。
- 使用本地 PostgreSQL `localhost:5432`、用户名 `postgres`、密码 `postgres` 验证表初始化和数据写入。
- 增加覆盖 CLI 参数、响应解析、分页、评论、存储工厂、API 和关键核心流程的自动化测试。

本次工作不包含：

- 不处理 `promt/dev-promt.md`。
- 不修改或接入 Qdrant。
- 不重建一套新的 WebUI 工程。
- 不进行与掘金接入无关的大规模重构。

## 现状与已发现问题

当前分支已经增加掘金的基础目录、爬虫入口、数据模型和存储实现，但尚未完整满足现有平台契约：

1. Web API 的平台枚举没有 `juejin`，API 请求会拒绝掘金任务。
2. WebUI 只有 Vite 构建产物，平台选择器中没有掘金。
3. 数据统计平台列表没有识别 `juejin`。
4. `--max_comments_count_singlenotes` 没有控制掘金评论上限，代码读取了掘金私有常量。
5. `--get_sub_comment` 对掘金没有效果，目前仅抓取一级评论。
6. 创作者模式未应用 `CRAWLER_MAX_NOTES_COUNT`，可能抓取全部文章。
7. 标准浏览器模式启动时丢弃了 Playwright 代理参数。
8. 搜索断点续传跳过已完成页面时没有推进真实游标，可能重复抓取或错页。
9. 指定文章模式为每个任务创建独立信号量，实际不能限制并发。
10. 指定文章和创作者 URL 的归一化不够稳健，查询参数或非标准尾部可能污染 ID。
11. 创作者列表先保存摘要、随后再保存详情，产生重复写入和无必要提交。
12. 数据库标识字段缺乏唯一约束，并发或重复任务存在重复行风险。
13. 掘金实现没有专属测试，接口响应变化和命令兼容性无法被及时发现。

## 方案选择

### 采用方案：沿用现有结构做最小兼容修复

后端继续使用已有 `media_platform/juejin`、`model/m_juejin.py`、`store/juejin` 和 SQLAlchemy 模型。Web API 在现有枚举和统计列表中补充掘金。WebUI 因源码未入库，将对当前 Vite bundle 做范围严格、可验证的静态修改。

优点：

- 与现有平台目录和调用方式一致。
- 改动集中，回归风险较低。
- 不引入新的前端工程或构建依赖。

限制：

- WebUI bundle 可维护性弱于源码修改，因此必须增加静态检查和浏览器验证。

### 未采用方案：重新创建 WebUI 源码工程

这能获得更好的长期维护性，但需要反向恢复组件、样式和构建配置，范围明显超出本次掘金接入需求。

## 架构与数据流

### CLI 和 API

CLI 继续通过 `cmd_arg.parse_cmd` 写入全局配置。Web API 的 `CrawlerStartRequest` 接受 `juejin`，`CrawlerManager` 继续将请求转换为同一组 CLI 参数，从而保证 API 与命令行行为一致。

ID 参数在命令入口统一归一化：

- 文章接受纯 ID 和 `https://juejin.cn/post/<id>`。
- 创作者接受纯 ID 和 `https://juejin.cn/user/<id>`。
- URL 中的查询参数、片段和尾部斜杠不会进入 ID。

### 爬取流程

搜索模式：

1. 按关键词调用搜索接口。
2. 使用接口返回的 cursor 推进分页。
3. 将搜索摘要与文章详情合并。
4. 保存文章。
5. 根据评论配置抓取一级评论及可选子评论。
6. 正确记录页面、详情和评论断点状态。

详情模式：

1. 统一归一化文章 ID。
2. 使用共享信号量限制并发。
3. 获取文章详情和正文。
4. 保存文章并按配置抓取评论。

创作者模式：

1. 获取并保存创作者资料。
2. 分页获取文章，最多处理 `CRAWLER_MAX_NOTES_COUNT`。
3. 获取详情后保存最终文章数据，避免不必要的摘要重复写入。
4. 按配置抓取评论。

### 评论

一级评论总量由现有 `CRAWLER_MAX_COMMENTS_COUNT_SINGLENOTES` 控制。

当 `ENABLE_GET_SUB_COMMENTS` 为真时，对 `reply_count > 0` 的一级评论调用掘金回复接口，分页抓取子评论。子评论沿用 `JuejinComment` 模型：

- `comment_id` 为回复 ID。
- `parent_comment_id` 为一级评论 ID。
- `content_id` 为文章 ID。

一级评论与子评论通过同一个存储回调写入，保持其他平台的行为模式。

### 存储

继续通过 `JuejinStoreFactory` 选择存储实现。数据库存储使用标识字段更新或插入：

- 文章：`content_id`
- 评论：`comment_id`
- 创作者：`user_id`

数据库模型为这些业务标识增加唯一约束。初始化新数据库时直接创建正确结构；已存在旧表时，测试会明确报告需要迁移，避免静默产生重复数据。

PostgreSQL 验证包含：

1. 初始化 `media_crawler` 数据库及掘金表。
2. 写入一条文章、一条评论和一条创作者记录。
3. 重复写入相同业务 ID，确认执行更新而非新增。
4. 查询确认字段和值正确。

## Web API 与 WebUI

Web API：

- `PlatformEnum` 增加 `JUEJIN = "juejin"`。
- 数据文件统计的平台识别列表增加 `juejin`。
- API 命令构建继续复用现有通用逻辑。
- 增加请求模型和命令构建测试。

WebUI：

- 在现有平台配置中增加值为 `juejin`、显示名为“掘金/Juejin”的选项。
- 使用通用文章 ID 和创作者 ID 输入提示；无需新增专属表单字段。
- 没有可用的掘金本地图标时，沿用现有通用图标表现，不额外引入网络资源。
- 修改后检查 bundle 中平台列表和请求 payload，并通过浏览器实际选择掘金、填写参数和发起请求。

## 错误处理

- HTTP 非 200、掘金 `err_no != 0`、超时和解析异常统一转换为 `DataFetchError` 或 `ForbiddenError`。
- 单篇详情失败不终止整个搜索关键词，记录失败断点并继续后续内容。
- 评论或子评论单页失败记录日志；已获取数据保留，断点状态标记失败以允许重试。
- 空正文文章保留摘要和统计字段，避免丢失有价值元数据。
- 不支持的登录方式给出明确日志；公共读取场景不强制登录。

## 测试与验收

自动化测试至少覆盖：

- CLI 接受掘金平台及文章/创作者 URL，正确写入配置。
- API 请求模型接受 `juejin`，命令构建包含正确参数。
- 搜索、详情、创作者和评论响应解析。
- 搜索 cursor 分页及断点跳页。
- 创作者文章数量限制。
- 一级评论数量限制和子评论开关。
- 指定文章共享并发限制。
- 所有存储选项的工厂映射。
- SQLite 或隔离数据库中的 upsert 行为。
- WebUI bundle 包含掘金平台配置。

验收命令包括：

- 掘金相关定向测试。
- `uv run pytest -q tests`，已有与本次无关的失败需单独说明。
- Python 编译检查。
- PostgreSQL 初始化和写入验证。
- 浏览器打开 WebUI，确认掘金可选且 API 请求成功进入后端。

## 兼容性与回滚

修改遵循现有公开命令和配置名称，不删除旧配置。现有平台逻辑原则上不变。各改动按 CLI/API、爬取核心、评论、存储和 WebUI 分组，出现回归时可按组回滚。
